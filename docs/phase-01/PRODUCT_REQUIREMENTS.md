## 1. Product overview

### 1.1 What the product is (specified, not built)

PSX Intelligence AI is specified as a Pakistan Stock Exchange (PSX) intelligence product for retail and research users: market overview, company exploration and intelligence, financial-statement and analysis views, sector context, news, valuation, probabilistic forecasting, probabilistic recommendations, risk views, portfolio planning aids, screening, AI-assisted research, alerts, report generation, and the administration/monitoring surfaces that keep the data and agents honest. It is an **information and analysis product**, not a trading terminal and not a broker.

### 1.2 What the product is NOT

- Not a trading platform. No order, execution, settlement, margin, or broker-account feature is specified.
- Not investment advice. Forecasts and recommendations are probabilistic, evidence-based, and never guaranteed; every such surface carries uncertainty and a disclaimer (see §2.4).
- Not a redistributor of a live PSX feed. No feature authorises resale or republication of PSX market data. Commercial redistribution requires a prior licence/terms check (UNVERIFIED — check V15).
- Not a guarantor of coverage. No module claims "all PSX companies" until the company master registry is reconciled and evidenced company by company (check V13; current status in the reference scaffold's `coverage.json`: `not_built`, every company `unknown`).

### 1.4 Users (all modules)

- **Visitor (unauthenticated):** public landing page and previews only (Module 1). No personal data, no portfolio, no alerts.
- **Registered user (authenticated):** full authenticated modules (3–19 as applicable), personal portfolio plans, screener saves, alerts, and report history — within their own account only.
- **Research user (authenticated, same permissions as registered user for spec purposes):** heavier use of Modules 17 and 19; no extra data privilege is assumed. Any future "analyst" role is a Phase 2 access decision, not a Phase 1 assumption.
- **Administrator:** Modules 20–21 only, plus read access to the same user surfaces for support/diagnosis under audit logging. Admin access never grants trade execution (none exists) or silent data correction (see §2.3).
- **Agent / job (non-human actor):** collection, analysis, and monitoring jobs that act only through the backend dependencies named per module, under the provenance and audit rules in §2. Agents never act as users and never bypass authentication or rate limits.

### 1.5 Non-goals (Phase 1 spec explicitly excludes)

- Real trade execution, broker integration, margin/settlement, or portfolio sync with a broker account.
- Paid tiers, payment collection, subscriptions, or any checkout flow.
- Live polling at a frequency that violates a source's rate limits, or any bypass of authentication/access controls.
- Full-scale live data collection in Phase 1 (documentation + read-only inspection only).
- Guaranteed forecasts, guaranteed returns, price targets presented as certainties, or recommendations without uncertainty and disclaimer.
- Republication/resale of PSX data, or any claim of PSX endorsement/affiliation (both libraries are unofficial and unaffiliated with PSX).

## 2. Global rules (apply to every module; module sections add specifics, never contradict these)

### 2.1 Cost rule — PKR 0

- No module may require a paid API, subscription, hosting, database, storage, monitoring, or AI/LLM service to deliver its core function. If a module's ideal version would need one, the module spec must state (a) the zero-cost degraded behaviour that ships instead, and (b) the item as BLOCKED pending a separate approval + "free insufficient" record.
- "Free tier" claims in a module spec must name limits, expiry, and card requirements from the provider's own terms, or be labelled UNVERIFIED. Local hardware/electricity/internet are external operating expenses, not project spend and not "free".
- Cost monitoring (Module 21) therefore monitors *project* spend (target: PKR 0) and *usage against free limits*, plus local resource use as an operating note — it does not monitor a paid bill that must not exist.

### 2.2 Data-provenance, time, stale / missing / conflict rules (from the reference scaffold — carried forward)

Every data record displayed or used by any module must carry, and every user-facing surface must be able to show on demand:

- `source` (named source/library/route, e.g. `psx-dps`, `psxdata`, PSX portal, SECP — only if verified for that field);
- `source_timestamp` — the source's own publication time, normalised to Pakistan Standard Time (Asia/Karachi, PKT);
- `collected_at_pkt` — when this system collected it, in PKT;
- `freshness` — age at display/collection time, with a stale flag when older than the module's stated max age (see per-module sections; market snapshot defaults are to be set by the data team, not guessed here — the scaffold cites 60s market-aware TTLs for `psx-dps` as a README claim, not as this product's committed TTL).

And the following are non-negotiable behaviours:

- **Stale is flagged, never silently presented as live.** A stale quote/index/price shows its source timestamp and a stale badge; it is never relabelled "live" or "real-time" because it was fetched recently.
- **Missing sessions are recorded, never filled.** A missing trading date/session appears as a gap with a "no record" note. No estimated, interpolated, or carried-forward price is presented as an actual price. (Illustrative example only — not a real quote: if 2026-11-03 has no record, the chart gaps on 2026-11-03; it does not draw a line through an invented value.)
- **Conflicts are kept side-by-side, never silently merged.** If primary and backup sources disagree on a price, both values, both sources, and both timestamps are visible, with the primary marked as the displayed value and the conflict flagged. The user (and admin) can see the disagreement; the system does not pick a silent average.
- **Raw vs processed separation.** Raw source payloads are stored separately from processed records. A processed value must be traceable to its raw payload.
- **No "real-time" label without a source timestamp.** The words live / real-time / current may appear only alongside the source timestamp and freshness they describe.

### 2.3 Correction, audit, and honesty rules

- No silent data correction. Any correction to a stored record creates a new version with reason, actor (user/admin/job), and timestamp; the prior version remains auditable.
- Every admin action (Module 21) and every agent action that writes, refreshes, or flags data (Module 20) is logged with actor, time (PKT), target, and outcome.
- Coverage honesty: any list, count, or "all companies" phrasing must be backed by the company master registry (check V13). Until then, surfaces show "coverage: verified for N companies; others unknown" or equivalent — never a bare total that implies completeness. The known count disagreements (~496 trading symbols vs ~1,029 listed instruments vs 1000+ tickers; 38 vs 37 sectors) must be explained on any surface that shows a count, because the numbers count different things.
- No invented endpoint, field, price, or capability. If a module needs a field that is UNVERIFIED, the module's acceptance criteria include the verification check that would prove it (V-number), and the feature ships degraded (field shown as unavailable with reason) until then.

### 2.4 Forecasts, recommendations, and uncertainty (binding display rules)

- **Horizons (fixed):** 1 day, 1 week, 1 month, 3 months, 6 months, 12 months. Every forecast surface must state which horizon it shows; a forecast without a horizon label is non-compliant. Short/medium/long groupings, if used in UI copy, must map to these horizons explicitly (e.g. short = 1 day / 1 week; medium = 1 month / 3 months; long = 6 months / 12 months — the mapping itself must be shown on the surface, not assumed).
- **Probabilistic only:** every forecast shows a range and/or scenarios (e.g. bear / base / bull with stated assumptions — illustrative labels only; the scenario definitions belong to the formulas team and must be consistent across Modules 12, 13, and 17), plus an uncertainty indicator. A single point price without a range is non-compliant.
- **Actual vs predicted history:** every forecasting surface that shows a prediction must offer its track record for the same horizon (past predictions vs actuals, with error shown), or an explicit "no track record yet for this horizon" state. A model with no track record must not be presented as proven.
- **Recommendations:** BUY / HOLD / SELL / WATCHLIST are probabilistic recommendations with uncertainty shown (confidence/range, key drivers, and what would change the recommendation). They are not guarantees, not investment advice, and not trade instructions. Every recommendation surface carries a disclaimer to that effect and a link/pointer to the evidence (Module 5/6/7/11/14 inputs) behind it.
- **No execution wiring:** no recommendation, forecast, alert, or portfolio suggestion may trigger, pre-fill, or link to a trade order. There is no order flow to link to in Phase 1 scope, and Phase 2 planning must not add one without a separate, explicit decision.

### 2.5 Security and privacy (global baseline; modules add specifics)

- Authentication (Module 2) is the only path to authenticated modules; no module may expose another user's portfolio, alerts, screener saves, or reports.
- No secrets, API keys, broker credentials, or passwords are stored, requested, or assumed in Phase 1. Any future external-service credential would need the secure-credential flow of the deployment environment (to be specified in Phase 2 planning, at PKR 0) — never plaintext, never in code, never in a document.
- Personal data minimisation: the product needs an account identifier, authentication data, and user-created artefacts (portfolios, screeners, alerts, reports) — nothing else is specified. No tracking, advertising, or third-party analytics SDK is specified (any such addition would need a privacy review + PKR 0 check).
- Rate-limit and terms compliance: every external fetch respects the source's stated limits and terms (see §2.2 and per-module external-integration sections). A `429` or equivalent is a stop/backoff signal, never a prompt to retry harder.

### 2.6 Accessibility, language, and display basics (global)

- All user surfaces show market timestamps in PKT with the source timestamp available; dates are unambiguous (day-month-year or ISO on data surfaces).
- Numbers show units and currency (PKR where applicable) and state whether a value is a price, change, percent, ratio, or count — never a bare number on a financial surface.
- Language: English is the specified UI language for Phase 1 scope. Any Urdu/Roman-Urdu surface is a future localisation decision, not assumed here. (This is a spec decision for Phase 2 planning to revisit; it does not describe the user's own language preferences.)
- Every surface that can be empty (no data, no coverage, no track record, model unavailable) has a designed empty state with a reason — never a blank panel or a zero presented as a real value.

### 2.7 Testing strategy — global rules (strategy only; no test is claimed passed)

- **Offline/fake-client first:** collection, provenance, stale, missing, and conflict logic must be testable with fake clients/fixtures, without a live PSX call (as demonstrated by the reference scaffold's offline-test pattern — that pattern is referenced, not re-claimed as this project's suite).
- **Golden-file / snapshot tests** for any computed display (ratios, technicals, valuation, forecasts): a fixed input fixture must produce a fixed, reviewed output; any change to the output requires a reviewed fixture update, not a silent drift.
- **Stale/conflict/empty-state tests** for every data surface: stale badge appears, missing session gaps (not fills), conflict shows both values, empty state shows a reason.
- **Uncertainty-display tests** for Modules 12/13/17/19: a forecast/recommendation fixture without a range, horizon, or disclaimer must fail its display test.
- **Security tests** for Modules 2/15/18/21: cross-user access attempts must fail; admin actions must appear in logs; no secret appears in logs or outputs.
- **No-live-claim rule:** a test is "passed" only after it runs and its output is recorded. Phase 1 records no project test passes. Small live-sample checks (V1–V4) are verification evidence, not a substitute for the test suite.

### 3.2 Module 2 — Registration / authentication

- **Objective:** let a person create exactly one account, log in and out securely, recover access without leaking account existence, and manage the minimum account data needed for Modules 3–19 — with no credential, broker, or payment data involved.
- **Users:** Visitor → Registered user (primary flow); Registered user (login/logout/session); Administrator (account administration via Module 21 only — never by direct database edit without a log entry).
- **Inputs:** registration: display name (optional/required to be decided in Phase 2 planning — this spec requires the decision to be recorded, not assumed), email address, password (rules to be set by the security design: minimum length, hashing, and breach guidance — not specified here beyond "never plaintext, never logged"); login: email + password; recovery: email only; session: token/cookie handling (mechanism deferred to security/architecture design at PKR 0).
- **Outputs:** account record; authenticated session; login/logout confirmations; password-recovery flow (generic messages); account-status states (active, locked after repeated failures — thresholds deferred to security design, must be recorded before build); error states that do not reveal whether an email is registered.
- **Features:**
  1. Registration (validation, duplicate-email handling with a generic message, confirmation step if the design requires email confirmation — the confirmation mechanism, including any email-sending route, is UNVERIFIED at PKR 0 and must be decided in Phase 2 planning; until then, registration must not assume a paid email service).
  2. Login / logout (session creation/invalidation; "remember me" only if the security design approves it with an expiry — not assumed).
  3. Password recovery (request + reset; generic success message regardless of account existence; reset link expiry; single-use handling — details deferred to security design).
  4. Session security (expiry, invalidation on password change, concurrent-session handling — rules deferred to security design, must be recorded before build).
  5. Account basics: view own account identifier + display name; change display name; change password (requires current password); delete/close account request (handling + data-retention rule deferred to legal/security design; until decided, the surface shows the request state, not a silent delete).
  6. No social-login, broker-login, or payment-linked account feature is specified. Any future addition needs its own security + PKR 0 review.
- **User interactions:** fill registration form; confirm (if required); log in; log out; request recovery; reset password; view/change own account basics; request account closure. No interaction exposes another user's account.
- **Required data / APIs:** no external market data. Email-sending route (if confirmation/recovery email is required): UNVERIFIED at PKR 0 — no provider is named here; Phase 2 planning must document a zero-cost route or design the flow without email (e.g. in-app recovery codes handled under the security design) and record the decision. Do not assume a free email API exists.
- **Backend dependencies:** auth service (registration, login, session, recovery, password-change); validation service; audit-log writer (Module 21 log store). No market-data backend is required for auth alone.
- **Database dependencies:** user account store (identifier, email, password hash only — never plaintext password, never password in logs); session store (expiry-aware); audit-log store (shared with Module 21). No portfolio/screener/alert tables belong to this module (they belong to Modules 15/16/18, keyed by user identifier).
- **AI agent dependencies:** none. No agent may create, access, or reset a user account.
- **External integrations:** none specified. Any email provider, if later required, is a separate integration decision under PKR 0 + privacy review — not part of this module's acceptance.
- **Security requirements:** passwords hashed with a current, reviewed algorithm (algorithm choice deferred to security design — never MD5/SHA-1/plaintext, never logged); generic responses for login/recovery failures (no user enumeration); rate-limiting/lockout on auth attempts (thresholds deferred, must be recorded); session tokens never in URLs/logs; all auth events logged (success/failure without passwords); account-closure handling must not silently delete audit logs.
- **Testing (strategy only):** registration validation + duplicate handling (generic message); login success/failure (generic failure message); recovery non-enumeration test; session expiry/invalidation tests; cross-user access test (user A cannot view/change user B's account); password-never-in-log test (log fixtures contain no password or hash); lockout/rate-limit tests once thresholds are recorded.
- **Acceptance criteria:** (a) a visitor can register, log in, log out, recover, and change password through the specified flows; (b) no flow reveals whether an email is registered; (c) no plaintext password or password hash appears in any log, output, or error; (d) sessions expire/invalidate as per the recorded security rules; (e) admin account actions go through Module 21 with a log entry, never by silent direct edit; (f) if no zero-cost email route is documented, registration/recovery ship with the recorded non-email design — not with an assumed email provider.

- **Features:**

  2. Market-status indicator (open/closed/unknown + session note; never inferred from a stale timestamp alone).
  3. Breadth panel (advancers/decliners/unchanged + total basis + as-of timestamp).
  4. Top gainers / top losers (ranked, with price, change %, volume if verified, source timestamp; ranking metric stated).

- **User interactions:** view dashboard; sort/filter tables within the stated metrics; click a security → Module 5; click a sector → Module 9; click a headline → Module 10; click an opportunity pointer → Module 13/16 detail; manual refresh (rate-limited). No trade, order, or alert-creation action lives on this dashboard except a clearly labelled link to Module 18.
- **Required data / APIs:** whole-market snapshot + index levels/constituents (candidate: `psx-dps` — UNVERIFIED as working integration, V1); backup snapshot/EOD (candidate: `psxdata` — V2); sector summaries (candidate: either library's sector route — taxonomy conflict noted, V1/V2/V13); news headlines (Module 10 dependencies). - **Database dependencies:** market snapshot store (raw payloads separate from processed snapshots, §2.2); index store; sector store; news-headline store (Module 10); user-preference/watchlist store (if used for personalisation — keyed by user, never shared). No portfolio tables belong here.
- **AI agent dependencies:** none required for core dashboard numbers. Optional agent role (deferred, Module 20): a market-summary agent that drafts the dashboard's textual summary — if used, its output is labelled as agent-drafted, shows its data as-of time, and never overrides a number. Core numbers must render correctly with no agent available.
- **External integrations:** PSX portal data via candidate libraries only (V1/V2). No broker, payment, or push provider is specified for this module.

### 3.12 Module 12 — Forecasting

- **Objective:** produce probabilistic price/forecast views for a company (and, where defined, an index/sector) across the six fixed horizons, with scenarios, uncertainty, method, inputs, and actual-vs-predicted track record — so a forecast is read as a distribution over futures, never as a promised price.
- **Users:** Registered user (primary); Research user; Administrator (diagnosis + model health via Modules 20–21).
- **Inputs:** company/index identifier; horizon selection (1 day, 1 week, 1 month, 3 months, 6 months, 12 months — §2.4); scenario view selection (bear/base/bull or the formulas/model team's scenario set — scenario definitions must be shown, not assumed); history-range selection for the actual-vs-predicted view (verified dates only); model selection IF multiple models are defined by the modelling team (model identity + version must be shown; an undefined model never appears).
- **Outputs:** forecast panel per horizon (predicted range, central tendency as defined by the model team, scenario values with assumptions, method + model version, inputs + as-of time, uncertainty indicator); scenario comparison (assumptions side-by-side); forecast history (past forecasts for the same horizon, each with its prediction time, predicted range, and the actual outcome once known); actual-vs-predicted table/chart (error shown per the model team's error definition; missing actuals shown as "actual not yet known", never as zero); track-record summary per horizon (only over evidenced past forecasts; "no track record yet" where none exists).
- **Features:**
  1. Horizon selector (six fixed horizons; no custom horizon is offered unless the model team defines and records it as an additional, labelled horizon — the six remain the standard set).
  2. Scenario display (scenario assumptions shown alongside values).
  3. Uncertainty display (range + uncertainty indicator on every forecast; a point forecast without a range is non-compliant, §2.4).
  4. Method/model transparency (method, model version, inputs, as-of time, training/estimation window as recorded by the modelling team — training data must be verified data only; a model trained on invented or unverified data must not ship).
  5. Forecast history + actual-vs-predicted (per horizon; error per model-team definition).
  6. Track-record honesty (per-horizon summary over evidenced forecasts only; no cherry-picked horizon presented as overall accuracy).
  7. Degradation (if no model is available for a horizon/company, the panel states "no forecast available for this horizon" with reason — it does not fall back to a price, a trend line relabelled as a forecast, or another horizon's forecast).
- **User interactions:** select company/index + horizon; switch scenarios; view method/inputs/track record; view actual-vs-predicted history; compare horizons (each horizon's panel keeps its own horizon label — comparison never merges horizons into one number). No trade action; no forecast is actionable as an order.
- **Required data / APIs:** price history (V1/V2, verified dates only); statement/fundamental inputs where the model team defines them (Modules 6/7, verified periods only); sector/market inputs where defined (Modules 9/3). Model definitions, scenario definitions, and error definitions: DEFERRED to the modelling/formulas teams — this module requires them but does not invent them. Any model requiring historical intraday data is BLOCKED (V14) until such data is verified.
- **Backend dependencies:** forecasting service (model-team methods, versioned per horizon); scenario service; forecast-history service (stores every issued forecast with prediction time + range + model version, so actual-vs-predicted is auditable); actuals service (verified actual prices only, never estimates); track-record service (per horizon, evidenced forecasts only).
- **Database dependencies:** forecast store (company/index, horizon, prediction time, model version, predicted range/scenarios, inputs reference, as-of times); actuals store (verified prices, Modules 3/5); forecast-history/track-record store (derived from the forecast store + actuals, never hand-edited). A forecast row without horizon + model version + prediction time must not display.
- **AI agent dependencies:** forecasting agent(s) (Module 17/20 family, as defined by the agents team): the agent that produces or post-processes a forecast must be identified (agent + version) on the forecast panel. If no agent/model is available, the degradation state in Features (7) applies. No agent may present a forecast without a range, horizon, or model identity.
- **External integrations:** price/statement/sector candidates only (V1/V2/V3/V13). No external forecasting vendor, paid model API, or broker signal feed is specified.
- **Security requirements:** read-only for users; forecast history immutable (a past forecast, once issued, is never edited — corrections create a new forecast version with a note, and the original remains in the track record); model-version traceability; disclaimer + uncertainty on every forecast surface (§2.4); no forecast linked to a trade order.
- **Testing (strategy only):** golden-file tests (fixed verified inputs → fixed reviewed forecast ranges per model version + horizon); range-presence tests (a forecast without a range fails display tests); horizon-label tests (every panel states its horizon); history-immutability tests (issued forecasts cannot be silently edited); actual-vs-predicted tests (error computed per the recorded definition, missing actuals shown as not-yet-known); degradation tests (no-model state, no fallback forecast); agent-identity tests (displayed forecasts name their agent/model version).
- **Acceptance criteria:** (a) forecasts render per horizon with range, scenarios + assumptions, method/model version, inputs, as-of time, and uncertainty; (b) actual-vs-predicted history exists per horizon or states "no track record yet"; (c) issued forecasts are immutable in the track record; (d) no-model horizons show a reasoned unavailable state, never a fallback forecast; (e) no forecast surface contains a trade element or a guarantee.

## 4. Cross-module consistency rules (Phase 2 planning must enforce)

1. **One definition per concept.** A ratio, valuation method, forecast model, risk indicator, health band, recommendation rule, sector taxonomy, or category list has exactly one recorded definition + version. Modules that display it link to that definition; they do not redefine it. (Owners: formulas/modelling/data/agents teams; Team 1's role is to require the linkage, not to define the formulas.)
2. **One value per as-of time.** For the same company, metric, and as-of time, Modules 5, 7, 8, 11, 12, 13, 14, 15, 16, 17, and 19 must show the same value (or the same "unavailable" state). A mismatch is a defect, not a rounding difference — unless a rounding rule is recorded by the owning team.
3. **One coverage truth.** The company master registry + per-company coverage records (V13) are the single source for "verified / unknown" language on Modules 1, 3, 4, 5, 9, 16, and 21. No module keeps a private coverage count.
4. **One provenance truth.** Source, source timestamp (PKT), collected-at (PKT), freshness, and raw-payload reference (§2.2) are carried identically wherever a value appears. A value shown without provenance on one surface but with provenance on another is a defect.
5. **One uncertainty truth.** A forecast's range/scenarios (§2.4) and a recommendation's uncertainty (§2.4) are the same wherever they appear (Modules 5, 12, 13, 16, 17, 19). A surface that drops the range/uncertainty is non-compliant even if its number matches.
6. **No execution anywhere.** No module, link, button, or agent action in this specification creates, implies, or connects to a trade order. A Phase 2 addition that introduces execution must be treated as a scope change requiring a separate, explicit decision — not as an implementation detail.
