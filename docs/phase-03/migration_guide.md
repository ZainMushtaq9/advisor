# Phase 3 — Migration Guide

## Revisions (in order)

1. `20261104_0001` — Phase 2 probe table only. Kept in Phase 3;
   its history stays auditable. (Its own docstring allowed dropping
   it in Phase 3; the coordinator decision was to keep it, because
   dropping gate evidence buys nothing.)
2. `645bcd200539` — Phase 3 schema (54 tables), autogenerated from
   `app.models.Base.metadata`, then hand-edited in exactly one

   from upgrade, and the autogenerated re-creation of
   `phase2_probe` was removed from downgrade. Both edits exist
   because upgrade must not drop a table downgrade then recreates
   — that asymmetry was found by a failing downgrade re-run and
   fixed before any claim was made (see defect register, Phase 3).
3. `20261104_0003` — immutability triggers (7 tables), versioned
   triggers (7 tables), quality CHECK constraints (21 tables).
4. `20261104_0004` — independent-audit fixes: financial_statements
   quality CHECK (22nd table), NOT NULL grain sources, partial
   unique current indexes, hash unique indexes, document-version
   is_current, restored ratio columns, data_sources verification

   + 8 versioned + 1 resolution-only + 2 marker-only).

## How to run

From `database/` with `DATABASE_URL` set (sourced from the
gitignored `database/.env`, mode 0600):

```
../backend/.venv/bin/python -m alembic upgrade head
../backend/.venv/bin/python -m alembic current   # must read 20261104_0003
```

Alembic `env.py` imports `app.models`; it needs `backend/` on
`sys.path`, which it now adds itself (repo-root fix, Phase 3).

## Fresh down/up cycle — actually run, twice

- Phase 2 cycle re-run (gate check, before Phase 3 code):
  downgrade base -> upgrade head, `20261104_0001`, exit 0 both ways.
- Phase 3 cycle: downgrade base -> upgrade head, `20261104_0003`,
  exit 0 both ways, 56 public tables, 14 triggers after upgrade.
  One intermediate downgrade failed (DuplicateTable on probe
  recreation; legacy trigger dependency on function drop) and both
  causes were fixed in the migration files, then the cycle was
  re-run clean. The failures are recorded, not hidden, because a
  migration whose downgrade fails is not a migration.

## Rollback warning

A full `downgrade base` drops all Phase 3 tables and the probe
table (via the Phase 2 migration's own downgrade). That is expected
for a full downgrade and is why a verified backup must exist before
any major schema change (see `backup_and_restore.md`). Never run
`downgrade base` against a database holding production data without
a verified backup first.
