# PSX Intelligence AI — Phase 1: Data Source Risk Register

**Budget:** PKR 0 absolute. Mitigations below use only free, local, or already-evidenced
means. Where a mitigation would require a paid service, the register says "no paid
mitigation under PKR 0 — accept / reduce scope" instead of introducing one. Local
hardware, electricity and internet are external operating expenses, never called free.
**Scope:** Phase 1 only. Likelihood and impact are JUDGEMENTS (labelled as such, not
data) to prioritise Phase 2 checks. Nothing here claims a risk has been tested live.
**No real trades:** the system must NOT execute real trades initially. Risks R-01–R-14
are data/licensing risks; trade-execution risk is out of scope because execution is
out of scope. If execution is ever proposed later, it needs a separate risk assessment
and explicit user approval — it is not authorised by this register.

## Scale (judgement, not data)

- **Likelihood:** Low / Medium / High — judgement about Phase 2, given Phase 1 evidence.
- **Impact:** Low / Medium / High / Critical — judgement about harm if the risk
  materialises (wrong data shown, licence breach, product blocked, user misled).
- **Owner phase:** the phase that owns the mitigation. All mitigations in this file are
  specified in Phase 1; most are executed/verified in Phase 2. No mitigation is claimed
  as done.

| R-02 | **Multi-node 404 quirk** (some dps.psx.com.pk nodes return 404 for data routes while serving the website). | High | Medium | Reuse the psx-dps node-pool/probe/pin/re-probe behaviour as a requirement (do not re-implement blindly — verify it on read-only inspection); treat a 404 as "wrong node", not "no data", and never as proof a symbol is delisted. | Phase 2 | Re-probe node pool; if no node serves data, fall back to psxdata snapshots; record the 404 episode in coverage notes, do not delete coverage rows. |

| R-10 | **Rate-limit / block risk** (no PSX-published limit; FRED 120/min reported-not-contractual; World Bank/IMF/SBP/PBS limits unstated; SECP access can be restricted, with a scraping precedent). | Medium | High | Throttle conservatively below any reported figure (psx-dps 1 req/s library throttle; FRED well below 120/min if ever cleared); cache aggressively (scaffold cache/backoff rules); treat 429/block as a hard stop for that provider in that run (project rule); never bypass auth, access controls or rate limits; never scrape SECP or any source against its terms. | Phase 2 | Back off, cache-serve labelled-stale data, reduce polling frequency, and log the block; do not rotate keys, nodes (beyond the documented psx-dps node pool), IPs or accounts to evade a block. |
| R-11 | **Stale-data risk** (off-hours PSX values, prior-day landing values, lagged annual macro, revised WEO/CPI/GDP vintages, FRED ALFRED vintages). | High | High | Scaffold rules, enforced: every record carries `source`, `source_timestamp`, `collected_at_pkt`, `freshness`; stale flagged, never silently presented as live; missing sessions recorded, never filled with estimates; conflicting prices kept side by side with provenance, never silently merged; vintage/edition recorded for every macro pull. | Phase 2 | Display the stale flag + source timestamp prominently; if freshness cannot be established, display "freshness unknown — do not use as live" and do not use the value in any alert, signal or summary that implies currency. |
| R-12 | **Silent-merge / provenance-loss risk** (sector-count mismatch 38 vs 37; CPI originator vs republisher; WEO vs WDI methods; renamed symbols). | Medium | High | Provenance-first design: raw payloads stored separately from processed records (scaffold); no cross-source merge without a mapping table + method note; every derived figure cites source + vintage + universe. | Phase 2 | Split the merged figure back into its source components, label the conflict, and re-issue any summary that relied on the merge. |
| R-13 | **Third-party-library risk** (psx-dps/psxdata unofficial + unaffiliated; psxdata alpha; World Bank/IMF/FRED clients all third-party; libraries can change, break or be abandoned). | Medium | Medium | Pin versions; record library licence + maintainer status per library; keep the collector's core (provenance/PKT/stale/conflict) in stdlib-only code (scaffold pattern) so a library failure does not corrupt core records; no library is treated as endorsed by its data owner. | Phase 2 | Pin to last working version, fall back to the other library or to publication downloads, and log the library failure as a coverage gap — do not vendor-patch a library silently. |
| R-14 | **Scope-creep risk — paid fallbacks, live trading, bulk redistribution** (pressure to "just buy the feed", "just execute", "just publish the dataset" when a free gap bites). | Medium | Critical | PKR 0 + no-real-trades gates are written into the Licensing Policy and this register; any proposal to spend, trade or redistribute needs a separate, explicit user decision outside Phase 1 — it is never implied by a gap, a deadline or a failed free source. | All phases (governance) | Refuse the creep in the current phase, document the gap and the refused option, and return the decision to the user with the limitation stated plainly. No paid alternative is introduced by this register. |

## Risks deliberately NOT added

- Broker/execution, order-routing, slippage, custody and market-risk risks are NOT in
  this register because real trading is out of scope initially. Adding them here would
  imply execution is planned. It is not.
- Paid-vendor risks (Eulerpool tiers, vendor lock-in, vendor price rises) are NOT
  registered as mitigations to buy, because no paid vendor is in scope under PKR 0.
  Eulerpool's exclusion is recorded in the Comparison file, not as a risk to manage
  by purchasing.
- Model/advice risks (hallucinated signals, investment-advice liability) belong to a
  later product-risk assessment, not to this data-source register, and are not claimed
  as assessed here.
